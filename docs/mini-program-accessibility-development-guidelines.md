# 微信小程序无障碍开发指导规范（草案）

> 状态：待评审草案。本文根据当前 Demo 的实现和已回填的走查结果整理，供团队讨论；尚未约定的设备、版本和数值门槛列在文末。

## 1. 范围与依据

本文面向微信小程序页面，包括原生小程序组件、表单、动态反馈、图片/视频，以及通过 `web-view` 承载的网页。ARIA 属性应以[微信小程序无障碍访问文档](https://developers.weixin.qq.com/miniprogram/dev/component/aria-component.html)和项目支持的基础库版本为准，不将 Web 网页的实现经验直接视为小程序运行时行为。

当前实测主要来自 Android 微信中的 Demo 和 Snapshot Companion。“实测观察”表示走查树中确实读到的结果；“开发要求”表示建议纳入后续规范的做法。Prompt 6、Prompt 7 的结果区尚未回填，其动态成功提示和设置项视觉效果不视为已完成实测。

## 2. 走查结果带来的优先改进

| 实测观察 | 对开发的要求 |
| --- | --- |
| 服务详情中“办理条件”和“办理步骤”的条目显示为无文本节点，虽然页面上能看到文字 | 列表的每一条都要在语义树中保留实际文本；不能只暴露列表角色、条目数或视觉内容。不要把唯一内容文本设为 `aria-hidden`。 |
| 表单标签、帮助文字、单选/复选状态在 deep 快照中可读；fast 快照漏掉了“活动日期”整组 | 完整表单和嵌套内容采用 deep 快照验收；浅层快照漏项时先加深读取，不能直接判定页面缺字段。 |
| Prompt 4 与 Prompt 5 对“联系人称呼”字段是否出现在语义树中的记录不一致 | 比较不同场景或录制结果前，先确认小程序版本、页面状态和快照层级相同；证据冲突时保留差异并复核，不按预期或源码替其中一方下结论。 |
| 表单错误摘要和各字段错误文本可读，但 `aria-invalid` 未在语义树中出现，且 WebView 调试通道不可用 | 将错误文字、错误与字段的关联、控件无效状态分开验收；错误文字出现不能证明无效状态已被读屏暴露。未读取到状态时标为未验证。 |
| 同一快照中可能包含前一层页面或屏外节点；搜索键盘弹出时结果列表曾暂时未被快照捕获 | 只依据当前屏幕可见节点判定；输入筛选后收起软键盘并重新取快照，避免把采集遗漏误判为页面空状态。 |
| 图片替代说明、可见图注、标题层级、按钮名称及收藏状态在对应走查中可读 | 保留这些已验证的实现方向，但仍须在目标微信版本和设备上复测。 |

## 3. 基本原则

1. **先选对原生组件。** 优先使用 `button`、`input`、`textarea`、`switch`、`radio`、`checkbox`、`picker`、`form`、`navigator` 等与交互目的匹配的小程序组件，保留其原生角色和状态。
2. **让内容本身可读。** 重要信息必须作为语义树中的文字节点出现。不能只用图片、颜色、布局位置或源代码里的属性表达信息。
3. **名称用简体中文。** 读屏名称、说明、错误、状态补充和媒体替代文字使用简体中文；ARIA 属性名、角色值、布尔值和关联 ID 仍按平台规定书写。
4. **按实际语义添加 ARIA。** 不机械地给每个节点添加 `aria-label`。优先使用可见文字、原生控件和正确的标签关联；需要补充操作目的或关系时再使用相应属性。
5. **以运行时语义树为验收证据。** 代码中写了 `aria-label` 或 `aria-invalid`，不代表系统已经把名称或状态暴露给读屏。必须检查目标运行时实际读到的节点。

## 4. 页面标题与导航

- 每个页面设置清楚的页面标题；页面主体有一个主标题，按内容层级使用二级、三级标题。微信小程序支持的标题语义可用 `aria-role="heading"` 和 `aria-level` 表达，随后用语义树确认角色与层级。
- 顶部导航栏标题和页面主体标题作用不同。验收时分别核对，不能只看到其中一个就判定标题层级完整。
- Tab、返回、跳转入口使用原生导航组件或控件，名称能说明目的。切换后重新获取快照并确认目标页面标题、Tab 选中状态和页面内容。
- 避免无名称的可点击容器、重复焦点和只显示图标而没有中文名称的操作入口。

## 5. 控件名称、说明与状态

- 按钮优先使用可见文字作为名称。卡片按钮需让用户知道打开什么内容；如需补充“查看详情”等操作目的，可使用简体中文名称，但不要重复拼接整张卡片的所有文字。
- 输入项使用持续可见的标签。占位提示用于示例或格式，不能代替标签。说明文字通过 `aria-describedby` 等平台支持的关联方式连接，并在节点树中检查关联结果。
- 单选、复选、开关优先采用原生状态，例如 `checked`。状态文字需要与控件状态同步；只改变旁边的文字或颜色不算状态覆盖。
- 非原生自绘控件只有在确有需要时才补角色、名称和状态，并同时实现键盘/触摸操作和状态更新。不要用 ARIA 把原生控件改成不匹配的角色。

## 6. 列表与重复内容

- 有序或无序内容应保留容器和条目层级；需要时使用 `aria-role="list"`、`aria-role="listitem"`、`aria-posinset` 和 `aria-setsize` 表达列表结构与位置。
- 每个列表项的实际文字必须能在语义树中读到。`aria-label` 不能代替对小程序运行时的验证；若父节点标签没有暴露，子项也不能因此变成空节点。
- 不要把条目中唯一的正文设置为 `aria-hidden="true"`。装饰用圆点、序号图形等才适合隐藏；真实文字应保留为可访问内容。
- 核对每项名称、顺序和列表位置。若只能从视觉画面读到文字，应记录为语义覆盖问题或未验证，不能判定通过。

推荐结构：

```xml
<view class="detail-list" aria-role="list">
  <block wx:for="{{items}}" wx:key="*this" wx:for-item="item">
    <view aria-role="listitem" aria-posinset="{{index + 1}}" aria-setsize="{{items.length}}">
      <text>{{item}}</text>
    </view>
  </block>
</view>
```

## 7. 表单、错误与动态反馈

- 每个字段提供中文标签、帮助文字、必填/可选提示和相应原生控件。单选和复选组还应提供组名及选择说明。
- 提交错误必须有可见文字，明确指出字段和修正方法；错误文字与字段的关系要能从语义树或读屏操作中确认。不能只用红色、图标或边框表示错误。
- 如使用 `aria-required`、`aria-invalid`、`aria-errormessage`、`aria-describedby`，要分别验证这些状态/关系是否在目标基础库、系统和控件上实际可读。发生错误后重新获取 deep 快照；未观察到 `aria-invalid` 时就记录“无效状态未验证”，不要用错误文案替代该结论。
- 筛选结果数量、错误摘要和提交结果可用 `aria-live`、`aria-atomic` 等提供动态语义。节点树中出现动态区域只证明语义存在，不证明 TalkBack 或 VoiceOver 已播报；播报需要单独实测。
- 对日期选择、弹窗和提交流程，要确认状态变化及返回路径。测试表单时使用独立空表单；可能产生真实数据的提交应先约定测试环境与操作范围。

## 8. 图片、视频与 WebView

- 有信息价值的图片提供简洁、准确的中文替代说明；纯装饰图片和装饰形状从读屏焦点流中隐藏。可见图注用于补充上下文，不必机械重复替代说明。
- 视频控件应有中文名称、简介及可获取的文字稿；没有素材时显示真实的待提供说明，不渲染不可用播放器。不要自动播放。
- 小程序 `web-view` 承载的是可访问的网页 URL，不能直接把小程序包内的本地 HTML 文件路径当作网页地址。URL 域名还需要满足小程序业务域名配置要求。
- WebView 内页面应使用语义 HTML、清晰标题、带名称的链接/按钮和正确标注的表单。小程序壳的 `aria-label` 不能代替网页内部语义；需要在真实设备上检查网页节点是否进入 Companion 语义树，并分别检查页面层级和可见区域。

## 9. 视觉、滚动与可操作性

- 状态不能只靠颜色区分；文字放大后允许换行，不遮挡控件；相邻操作之间有清楚间隔。
- 页面和列表滚动后，当前焦点和可见内容应保持可理解。滚动区域应有明确用途名称；不要让屏外或被覆盖的页面节点混进当前页结论。
- 做对比度、尺寸、遮挡或布局像素比较时使用 Screen Analyze；语义名称、角色、状态和关联一律依据 Snapshot Companion。

## 10. 开发验收清单

- [ ] 页面导航标题和正文主标题都能识别，标题层级连续。
- [ ] 每个可操作控件都有简体中文名称、正确角色和可观察状态。
- [ ] 列表的每一条正文都在语义树中出现；没有把唯一内容文本隐藏。
- [ ] 表单有可见标签、帮助、必填/可选说明；错误文字可见且能关联到字段。
- [ ] 控件状态和相邻状态文字同步；切换后重新取快照确认。
- [ ] 图片、视频等非文本内容有合适替代内容；装饰内容不造成多余焦点。
- [ ] 动态结果检查语义和实际播报，不把属性存在当作播报证据。
- [ ] 表单、嵌套列表和复杂页面使用 deep 快照；只把当前可见范围内节点作为页面证据。
- [ ] 语义树问题与纯视觉问题分别记录，未观测到的内容标为“未验证”。
